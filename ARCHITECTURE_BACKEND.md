# Архитектура Бэкенда (Spring Boot) ⚙️

**5000 Words Backend** — это RESTful API сервис, отвечающий за бизнес-логику обучения, сохранение прогресса, геймификацию и мультиплеер (дуэли).

---

## 🏛 Общая структура слоев

Бэкенд спроектирован на основе классической слоистой архитектуры (N-Tier Architecture), что обеспечивает четкое разделение ответственности (Separation of Concerns).

```text
[ HTTP Requests ]
       │
       ▼
┌─────────────────────────────────┐
│       Security Layer            │  (JWT Authentication, CORS)
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│      Controller Layer           │  (REST Endpoints, Validation)
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│        Service Layer            │  (Business Logic, Algorithms)
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│     Data Access Layer           │  (Spring Data JPA, Hibernate)
└────────────────┬────────────────┘
                 │
                 ▼
          [ PostgreSQL ]
```

---

## 🔐 Слой Безопасности (Security)

Авторизация построена на **Stateless JWT** (JSON Web Tokens). Сервер не хранит сессии в памяти.

1. **Генерация токена:** При логине (`/api/auth/login`) сервис сверяет хеш пароля (через `BCrypt`). Если всё верно, `JwtService` генерирует JWT токен сроком на 30 дней. Токен подписывается секретным HMAC-ключом.
2. **Фильтрация:** `JwtAuthenticationFilter` перехватывает все запросы. Он парсит заголовок `Authorization: Bearer <token>`.
3. **Авторизация:** Если токен валиден, фильтр извлекает `userId` и помещает его в `SecurityContextHolder`. Контроллеры получают пользователя через аннотацию `@AuthenticationPrincipal UserDetails`.

## 🧠 Ключевые сервисы и алгоритмы

### 1. Движок SM-2 (`SessionService`)
Отвечает за генерацию и проверку сессий.
* **Генерация сессии (`startSession`):** Выбирает слова для повторения, у которых `nextReviewDate <= today`. Если таких слов не хватает, добирает новые слова из базы, учитывая `SubscriptionLimits` (максимум 50 новых слов в день для Free-пользователей).
* **Проверка ответа (`finishSession`):** Рассчитывает новые параметры для каждого слова:
  * Если ответ правильный: увеличивает `streak` успешных ответов, умножает интервал (1 → 3 → 7 → 15 дней), немного повышает `easinessFactor`.
  * Если ответ неверный: сбрасывает `streak` в 0, `interval` в 1 день, понижает `easinessFactor`.

### 2. Геймификация (`StreakService` & `LeagueService`)
* **Система Лиг:** Лига пользователя рассчитывается на лету (`user.xp / 10000`). Это исключает рассинхронизацию данных. Бэкенд находит других пользователей в том же диапазоне XP, чтобы сформировать Лидерборд текущей лиги.
* **Стрики и Заморозка (Premium):** Учитывает непрерывные дни обучения. Если Premium-пользователь пропустил ровно 1 день, `StreakService` использует "Заморозку" (`lastFreezeUsed`), сохраняя стрик и отправляя на фронтенд флаг `freezeUsed = true`.

### 3. Социальная механика (`DuelService` & `FriendService`)
* **Друзья:** Статусная модель дружбы (`PENDING`, `ACCEPTED`, `DECLINED`). Лимит 5 друзей для бесплатных аккаунтов. Поиск пользователей нечувствителен к регистру (Case-Insensitive).
* **Дуэли:** Асинхронный мультиплеер. Создатель дуэли проходит случайно сгенерированный набор из 10 слов. Когда второй игрок принимает вызов, он получает *тот же самый набор слов*. По окончании бэкенд сравнивает точность (`accuracy`) и скорость прохождения, выявляя победителя.

## 🗄 Работа с Базой Данных

Используется **PostgreSQL** в связке со **Spring Data JPA**.

* **Оптимизация:** Для тяжелых запросов (например, Лидерборд) написаны кастомные JPQL запросы (`@Query`) и настроены индексы в БД (`idx_users_xp`).
* **Валидация:** Используются строгие ограничения на уровне Entity (`@Column(nullable = false, unique = true)`), что не позволяет создать дубликаты даже при сбое на уровне приложения.

---

## 🛑 Обработка ошибок (Error Handling)

Используется `GlobalExceptionHandler` (`@RestControllerAdvice`). Любое исключение (например, нехватка прав, превышение лимита друзей) перехватывается этим классом и отдается на фронтенд в едином формате JSON:

```json
{
  "status": 400,
  "message": "Бесплатный план ограничен 5 друзьями. Оформите Premium для безлимита."
}
```
Это позволяет фронтенду легко парсить ошибки и показывать понятные уведомления (toasts) или редиректить пользователя на экран покупки.
